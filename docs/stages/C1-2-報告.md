# C1-2 報告：回覆、按反應用群組表情與貼圖

## 做了什麼
- **圖鑑載入**（`yuki/emoji_catalog.py`）：`data/emoji/*.json` 維持最上層是 list（C1-1 格式不變）。「是否看過」放在旁邊的 `<伺服器ID>.meta.json`（`{"reviewed": false}`）：沒有 meta 檔＝沒看過；建圖鑑時只在沒有 meta 時才建（重跑不會把人工改的 true 蓋回 false，`use` 也保留）；載入時也接受 `{"reviewed":…, "items":[…]}` 單檔寫法。**沒有任何圖鑑被設成 reviewed=true。**
- 只用 `use=true` 且有 meaning 或 looks 的；名稱難念（非中英數、超過 20 字、長串十六進位或數字）或同名的給別名（表情 `e1…`、貼圖 `s1…`），程式記對照。
- **範圍控制**：新設定 `EMOJI_GUILD_IDS`（留空＝只有 `TEST_GUILD_IDS`）；只用「這個伺服器自己的」圖鑑，測試伺服器不會借主伺服器（`PROFILE_FALLBACK_GUILD`）的。主伺服器行為不變（沒有圖鑑、不放清單；只多了把 `:xxx:`、`[貼圖:…]` 清掉）。
- 啟動（on_ready）時用 `guild.emojis`／`guild.stickers` 比對：已刪的不用、改名的換新名、新增的只記 log。
- **回覆**（`prompts.py`、`brain.py`、`bot.py`）：reply system 加「群組自己的表情與貼圖」段（最常用 22 張表情＋最多 4 張貼圖，每行 `:名稱: 用法`，沒有 meaning 用 looks，截 60 字；不放範例句）；人設那句改成「一般表情符號和 XD 盡量少用；群組有自己的表情或貼圖可用時偶爾拿來代替，不要每句都用」。後處理：`:名稱:`→`<:名稱:ID>`（動圖 `<a:…>`）；清單外的 `:xxx:` 刪掉；模型自己寫的 `<:名稱:ID>` 不在圖鑑裡也刪；`[貼圖:名稱]` 抽出用 `stickers=` 另外附（只有貼圖時文字為空也能送）；表情＋貼圖合計一則最多 1 個（照出現順序，第一個有效的留下）。`_NAME_PREFIX` 改成不會把開頭的 `[貼圖:…]` 當名字吃掉。沒圖鑑的伺服器不放這段 prompt。
- **頻率保證**（`EmojiPacing`，規格沒寫，見待決定）：同頻道用過表情或貼圖後，接下來 2 則回覆不放清單、模型寫了也刪。理由：純靠 prompt 控制比例，這個模型浮動太大（見下）。
- **按反應**（`chime.py`、`bot.py`）：有圖鑑的伺服器，插話判斷 system 加最常用 10 張（名稱＋用法），user 訊息最後加一句提示（只放 system 時 20 則裡 0 則選 react，放在最後才有效）；`emoji` 欄接受名稱、`:名稱:`、別名或 unicode；有圖鑑時圖鑑以外的群組表情不按。次數限制沿用 B2（每 10 分鐘 3 個）。被叫到時回一句＋按反應：沒做（依規格）。
- **語音**：`speakable()` 刪 `<:名稱:ID>`、`<a:名稱:ID>`、`:名稱:`、`[貼圖:…]`（時間 `12:30:45` 不受影響）；語音回覆本來就不放表情 prompt。
- **評估**：`scripts/eval_emoji.py`（`--prepare` 從封存區挑題、`--catalog` 直接指圖鑑檔不看 reviewed）；`scripts/eval_chime.py` 加 `--emoji`、`--emoji-n`。題目與結果在 `data/eval_c1/`（不進 git）。
- 單元測試：新增 `tests/test_emoji_use.py`（16 個）與 `test_emoji_catalog.py` 的 10 個，涵蓋替換、刪壞名、一則上限、貼圖抽出、reviewed=false 不用、跨伺服器不用、別名、同步、頻率、bot 回覆與按反應流程、speakable。

## 測試伺服器圖鑑
`build_emoji_catalog --guild <測試伺服器>` 已跑（只用 REST）：**測試伺服器目前 0 個自訂表情、0 張貼圖**，圖鑑檔是空 list、meta 是 reviewed=false。所以測試伺服器要實測，得先上傳幾個自訂表情、重跑建圖鑑，再把 meta 改成 reviewed=true。

## 評估數字
評估用主伺服器的圖鑑（64 張，直接指檔、不看 reviewed）。回覆 50 則取自封存區 2026 年的真實片段（不同天、前 15 則當前文）；反應 20 則取自封存區（接著有人笑／恭喜的訊息：12 好笑、6 吐槽、2 里程碑），是代理標準，不是人工逐則挑的。每項跑兩次。

| 項目 | 標準 | 第 1 次 | 第 2 次 | 結果 |
|---|---|---|---|---|
| 回覆用到表情 | 10%～30% | 18%（9/50） | 16%（8/50） | 通過 |
| 回覆壞掉的 `:名稱:` | 0 | 0 | 0 | 通過 |
| 回覆一則兩個以上 | 0 | 0 | 0 | 通過 |
| 反應：選 react 且合適 | ≥ 70%（20 則） | 55%（11/20）；react 16 則、其中合適 11 | 55%（11/20）；同 | **未達** |
| 語音念出來含 `<:` | 0 | 0（106 句） | 0 | 通過 |
| 閒聊 30 句「有查」（越低越好，B 階段 13%、10%） | 不退步 | 13% | 7% | 通過 |
| 插話 50 題正確率（不放表情清單，等於 B 階段現況） | ≥ 78% | 78% | 78% | 通過 |
| 插話 50 題速度中位數（不放清單） | ≤ 0.6 秒 | 0.586 | 0.578 | 通過 |
| 插話 50 題正確率（**放 10 張清單＋提示**） | ≥ 78% | 74% | 74% | **未達** |
| 插話 50 題速度中位數（放清單） | ≤ 0.6 秒 | 0.618 | 0.609 | **略超** |

補充：
- 回覆用到的比例不靠 prompt 本身：不加頻率保證時，同樣 prompt 跑出 14%～40% 浮動；「大約幾成」「很少」這類話這個模型抓不準，最後靠 `EmojiPacing`（用過後 2 則不用）才穩定。有放清單的那幾則，模型自己用的比例約 23%～28%。兩次的後處理都沒有救到壞名稱的情況（原始就沒有兩個以上；原始壞名稱 0～1 次）。沒有發出貼圖（4 張貼圖都沒有使用紀錄，模型沒選）。
- 反應合適的判斷是 LLM 依 meaning 判，偏寬鬆（react 的 16 則裡 11 則合適）；抽出的 5 則：3 則合適、2 則（「氣死」配「平靜凝視」、「新武器很爛」配「輕鬆微笑已讀」）不合適，建議使用者看一下。模型偏愛用籠統的那幾張（平靜凝視、微笑已讀）。
- 反應只放 system 時 0/20；提示放在 user 訊息最後後升到 16/20（8～16 之間浮動）。放清單後插話正確率降 4 點：5 題變動（2 題由回覆變按反應、3 題 reply↔none 變動），同時修正了另外 3 題；`emoji-n 6` 也一樣 74%，沒有用。沒有清單時（現況、預設）完全是 B 階段的數字。
- 插話速度有加清單與不加清單都在 0.58～0.62 之間，跟 LM Studio 同時被 Yuki 使用有關，差距在雜訊範圍。

## 待 PM 決定
1. **反應 ≥70% 未達（55%）、放清單後插話 78%→74%、速度略超 0.6 秒**：模型很安靜，要它按反應就會有幾題把該開口的變成按反應。選項：(a) 接受，因為預設沒有 reviewed 的圖鑑、不會影響現況，等實測再看；(b) 不在插話判斷放清單，反應另外用一次獨立的小判斷（只在判斷結果是 none 時、閒置時才跑）；(c) 讓使用者看反應結果再調提示。我建議 (a) 先上測試伺服器看實際情況。
2. **頻率保證 `EmojiPacing`**（用過後接下來 2 則不用）是規格外加的；不要的話比例會超過 30%（約 30%～50%）。
3. 反應題目是代理標準（後面有人笑／恭喜），並不是人工挑的「值得理一下」；5 則人工抽看結果在結果檔 `data/eval_c1/results/emoji_final_*.json` 的 `human_check`。
4. `[貼圖:…]` 與表情同時出現時，保留文字裡先出現的那個（通常是表情，貼圖在最後）。
5. 圖鑑 reviewed 的切換方式是改 `<伺服器ID>.meta.json`；開發 PM 看完使用者回饋後再改。主伺服器要用，需另外在 `EMOJI_GUILD_IDS` 填入。
