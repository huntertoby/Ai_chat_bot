# A4 小修 — 規格

> 對應：`企劃.md` 階段 A4。三件互不相關的小事。

## 1. 人物檔案自動更新每分鐘空跑（開發 PM 自己改）
- 問題：`yuki/profile/auto.py` 的 `has_unmerged` 把「有新資訊、但資訊太少（< `min_facts`）又還沒有檔案」的人也算成還沒合併 → 每次閒置檢查都進 `run_once`、什麼都沒整理卻寫「人物檔案：更新完成」。
- 改法：新增 `mergeable()`，只列「有新資訊且（資訊 ≥ `min_facts` 或已有檔案）」的人；`has_unmerged` 和合併迴圈都用它。「更新完成」只在真的有抽取或整理時才寫，並附整理人數。
- 驗收：新測試 `test_few_facts_without_file_do_not_keep_it_busy`（第二次閒置直接 skip、不寫「更新完成」）；全部測試過。

## 2. 量「查不到時說不知道」（開發規格 6.4 表格最後一列，標準 ≥ 95%）
- 新增題目檔 `eval/unknown_cases.jsonl`：約 40 題，問**封存區裡確定沒有**的事（某人說過但其實沒說過的話、沒發生過的活動、不存在的日期事件；一半換句話說）。題目用真實成員名字才測得準 → 這個檔**不進 repo**（加進 `.gitignore`，跟 `eval/archive_cases.jsonl` 一樣）；repo 裡放一個用佔位名字的 `eval/unknown_cases.example.jsonl`（3～5 題）示範格式。
- 每題出題後要用 `search_chat` 同樣的查法確認真的查不到（避免題目其實有答案）。
- `scripts/eval_agentic.py` 加 `--expect-unknown`：每題回覆交給 LLM 判斷「有沒有表示不知道／查不到，而且沒有編造具體內容」；印出比例和失敗的題目。判斷用的 prompt 描述標準即可，不要放會被照抄的範例句。
- 跑一次（`--cases eval/unknown_cases.jsonl --real --expect-unknown`），結果寫進報告。LM Studio 要載著 Yuki 的模型。

## 3. 開發規格第 7、8 節照現況更新

- 第 8 節「可以刪除的檔案」：對照現在的檔案，已刪的拿掉；列出還能刪的。實際刪檔要先回報（會動到使用者的檔案）。
- 同時把 6.12 標為已完成（A2）、6.4 補上第 2 項的數字。
- 注意：工作目錄裡 `開發規格.md` 有別的 session 還沒 commit 的改動（第 2 節 MoE 重測表）。等它被 commit 後再改，避免把別人的改動混進來。
