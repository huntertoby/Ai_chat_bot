# D-22 插話判斷改用「模型機率＋門檻」— 規格

> 決定：`docs/決定紀錄.md` D-22（使用者：「好，交給開發 PM」）。目標：插話正確率 78% → 85%。
> 做法參考 Luna（讓模型對「該不該開口」給機率，過門檻才開口）；Luna 沒有授權條款，**只參考做法，不抄程式碼**。方向是**比 Luna 安靜**。

## 已確認（開發 PM 先做的）
- LM Studio（8001）的 `/v1/chat/completions` 在**關掉思考**（`reasoning_effort: "none"`）時會回 `choices[0].logprobs.content[i].top_logprobs`（每個位置前 5 名 token 和 logprob）。開著思考時 logprobs 是 null。`/v1/completions` 不回 logprobs。
- 被回覆的舊訊息不在最近對話時會補抓（`yuki/bot.py` `reply_ref`／`_fill_reply_refs`、`chime.fill_replies`）：先用 Discord 快取，拿不到就 `fetch_message`，每次最多 3 則，被回覆那句截前 40 字（`ReplyRef`），渲染成 `[小傑 回覆 阿明「…」]`。跟 Luna 一樣，這項不用改。

## 要做的
1. **機率從 logprobs 算**（`yuki/chime.py`、`yuki/llm.py`、`yuki/prompts.py`）：
   - 仍是**一次** LLM 呼叫（速度 ≤ 0.6 秒）。讓模型在輸出的**第一個決定位置**（例如 JSON 第一個欄位是「要不要開口」的是／否，或 action）給答案，從那個位置的 top_logprobs 算「開口」的機率：開口那類 token 的機率和 ÷（開口＋不開口的機率和）。
   - JSON schema 的限制可能讓 top_logprobs 反映的是限制前或限制後的分布，**先實測**確認算出來的數合理（明顯該插的題接近 1、明顯不該的接近 0）。不合理就改用不帶 schema 的短輸出（第一個 token 是答案，其餘欄位接在後面再由程式解析），仍是一次呼叫。
   - 拿不到 logprobs（null、找不到那個位置）時，退回模型自己寫的 `participate`，追蹤紀錄註明 `prob_source`。
   - `llm.py` 加取 logprobs 的方法或參數，不影響其他呼叫。
2. **門檻可調**：`CHIME_PROB_THRESHOLD`（config＋`.env.example`）；`CHIME_IN` 等級的門檻照舊對應（1 是預設），有設這個值就用它。追蹤紀錄寫機率、門檻、來源。
3. **掃門檻**：插話 50 題跑 **2 次**，門檻 0.5、0.6、0.7、0.8（同一次跑記下機率，門檻在程式外套用即可，不用每個門檻重跑）。看：正確率（三類）、代名詞題、里程碑 20／轉貼 20（`--only milestone`，跑 1 次）、速度中位數／P90。挑一個當預設：正確率最高者；相近時選**比較安靜**（門檻高）的。
4. **兩條規則變體**（只在評估確實變好才採用；兩次平均比基準多 ≥ 3 點，而且代名詞全對、里程碑 ≥ 80%、轉貼 ≤ 20% 沒退步）：
   - 有人接著她剛講的話說下去，即使很短，算是在跟她講話。（注意：現在的規則已有「接你剛講的話（包括很短的接話）」，先確認是否已涵蓋；已涵蓋就記錄「不用加」。）
   - 兩個人正在一來一往解釋事情、話還沒講完，不要插話。
   - 照 CLAUDE.md：描述標準，**不放範例句**。
5. **評估腳本**：`scripts/eval_chime.py` 加記錄機率、離線掃門檻的輸出。結果檔放 `data/eval_b/results/`，檔名含 `d22`。
