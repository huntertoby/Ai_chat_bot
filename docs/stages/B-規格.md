# 階段 B（B2 插話判斷、B3 防洗版、B4 先查再接話）— 規格

> 對應：`企劃.md` 階段 B、`開發規格.md` 6.1、6.2、6.13（第 1、2 層）。使用者要求 B 階段一起做完再審查。
> B1（看圖片）已完成，`yuki/vision.py` 的 `glance_images()` 給插話判斷用。

## 現況（要改的地方）
- `yuki/bot.py` `on_message`（約 381～460 行）：`called`（@、叫名字、回覆她、@ 她的身分組）或 `active`（注意模式，`attention_timeout` 內）就**每句都回**；其他訊息只進記憶緩衝。沒有插話判斷、沒有節流。
- `ChatLine`（`yuki/memory/writer.py`）沒有回覆關係；`to_messages`（`yuki/brain.py`）只有 `[名字] 內容`。
- LLM 一次只處理一個請求：`LMStudioClient._slots`（semaphore）。
- 語音（`yuki/voice/session.py`）有自己的 `should_reply`；這次**不改語音**（6.10 屬 D2）。
- Luna 互動是 C4：這次 bot 一律不判斷、不回（Luna 也是）。

## B3 防洗版與節流（先做，B2 建在它上面）
新模組 `yuki/throttle.py`（純邏輯、可測），`on_message` 使用：
1. **雜訊過濾**：bot、webhook、系統訊息（加入、置頂、加成…，`message.type` 不是 default／reply）、斜線或前綴指令（`/`、`!`、`.` 開頭）、空白、只有表情或沒內容的短反應（「ok」「笑死」「我去」之類，用規則判斷：去掉表情和標點後 ≤ 2 字，或在一個小清單裡）→ 不判斷、不回（照常進封存區）。
2. **大量重複**：同一字元連續 ≥ 10 次、或同一則重複 @ ≥ 3 次 → 不回、不進記憶。
3. **每頻道同時只處理一則**：同頻道正在產生回覆時，新的「沒被叫到」訊息不觸發；被叫到的排隊，等目前這則回完，把排隊期間的訊息合成一次回覆（不要連回三則）。
4. **頻道冷卻**：回完後同頻道 5 秒內不主動插話（被叫不受限）。
5. **tag 洗版**：同一人 60 秒內叫她 > 3 次 → 只回第一次，之後這個人冷卻 2 分鐘。
6. **對話紀錄去重**：連續重複的同一句（同人同內容）只留一則。
- 數字都放 config（有預設值）。

## B2 判斷是不是在跟她講話、要不要插話
新模組 `yuki/chime.py`：
1. **回覆關係進對話紀錄**：`ChatLine` 加 `reply_to`（被回覆者名字、是不是 Yuki、被回覆那句前 40 字）。`to_messages` 渲染成 `[小傑 回覆 阿明「…」] 內容`／`[小傑 回覆你「…」] 內容`。被回覆的那則不在最近對話裡時，用 Discord API 補抓（每次最多 3 則，失敗就略過）。
2. **prompt 自我指稱**（`reply_system` 共通規則）：跟你講話時的「你」就是你；別人說機器人、AI、她、Yuki 可能在講你；用第一人稱，不要用「他」稱呼自己。描述做法、不放範例句。
3. **插話判斷**（只有沒被叫到、沒被 B3 擋下的訊息）：
   - **去抖動**：同頻道最後一則訊息後 4 秒沒人再講，才判斷最新那則。
   - **LLM 忙就跳過**：`_slots` 被佔用時不排隊，直接放棄這次判斷。
   - 一次短的 LLM 呼叫，`response_format` JSON schema：`{"participate": 0~1, "action": "reply"|"react"|"none", "emoji": "...", "kind": "congrats"|"comfort"|"answer"|"addon"|"about_me"|"other", "reason": "一句話", "need_background": ["..."]}`。關掉思考、`max_tokens` 小。
   - 給模型看：`[你是誰]`（一兩句定位）、`[最近的對話]`（最近 15 則，含回覆關係）、`[最新訊息]`。最新幾則有圖時附最多 3 張低解析度（`vision.glance_images`）。
   - 判斷規則照 6.1 的表（里程碑恭喜、壞消息關心、全頻道開放問題且答得出、提到她或接她的話、有料可補 → 插；一般轉貼、一對一在聊、沒內容反應、她講不出東西 → 不插）。**Yuki 要比 Luna 安靜**。照 CLAUDE.md：描述標準，不放會被照抄的範例句。
   - `participate ≥ CHIME_THRESHOLD`（預設 0.7）且 `action=reply` → 走回覆（先處理 `need_background`，見 B4）；`action=react` → 對那則按表情（unicode 或群組表情名稱，找不到就不按）；否則不動。
4. **程式硬限制**：
   - `CHIME_IN=0~3`：0 = 只有被叫才回；1（預設）= 門檻 0.7、同頻道每 10 分鐘最多主動插話 1 次；2 = 0.6、5 分鐘；3 = 0.5、2 分鐘。按表情也算一次但另外計（每 10 分鐘最多 3 個）。
   - 同一個人、同一個 `kind`（例如 congrats）一天最多 1 次。
   - 有人對她說「沒問你」「閉嘴」「乾你屁事」這類 → 那個頻道 30 分鐘不主動插話（被叫仍回）。
   - **注意模式改成提示**：`active` 期間的訊息不再必回，改成走插話判斷，但 prompt 告訴模型「她剛講過話，這則比較可能是在跟她講話」，而且不受 10 分鐘限制（仍受 B3 冷卻）。
5. **追蹤紀錄**（A2）：每次插話判斷寫 `kind="chime"` 一筆（判斷 JSON、耗時、最後動作）。跳過的（LLM 忙、冷卻、限制）也寫一筆 `outcome=skipped` 並註明原因，方便事後調。

## B4 先查再接話（6.13 第 1、2 層；第 3 層不做）
1. **第 1 層（prompt）**：回覆時，對話裡有不熟的人、隊伍、比賽、事件，尤其是「最近」的，先查再接話，不要順著話裝懂。
   - 群組成員（名字在 `members_of` 裡）**只查封存區**，絕不上網（程式原本就擋成員名字上網，確認這條路還在）；不確定是不是成員就當成員。
   - 公眾人物、隊伍、比賽：上網查，關鍵字帶年份；講的時候帶「網路上說／新聞寫」，八卦不講得像確定的事。
2. **第 2 層**：插話判斷給的 `need_background`，在決定插話後交給回覆流程（例如放進 system 的一行「回覆前先查：…」），讓 agentic 迴圈去查；不插話就什麼都不查。
3. A5 留下的兩個改法（`search_chat` 查不到時明說、回覆前自我檢查）**這次不做**，等 B 驗收看情況。
