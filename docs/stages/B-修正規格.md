# 階段 B 評估後修正 — 規格

> 前提：`B-規格.md` 已實作（a5689ae），審查 9 項已修（6a88978）。評估結果見 `data/eval_b/results/`（不進 repo）。
> 這份只修評估沒過的地方。做法、數值照最保守的先做，結果寫進 `B-報告.md` 給使用者審查。

## 1. 成員名字誤擋公眾搜尋（`yuki/brain.py` `names_in`）
- 現在用小寫子字串比對：2 個字的英文成員名會擋掉任何含那兩個字母的英文搜尋（例：選手名裡剛好含成員名的字母）。
- 改成：名字有英文字母或數字時，要整個詞相符（前後不是英文字母或數字），不分大小寫；全是中文等其他字的名字照舊用子字串比對。
- 寧可多擋不要漏擋：名字裡夾中英文時，照子字串比對。
- 單元測試：英文短名不擋含它字母的長字；英文名獨立出現、前後接中文或標點都要擋；中文名照舊。

## 2. 洗版重播回覆太多（`yuki/throttle.py`、`yuki/bot.py`）
- 原因：tag 限制按「每人」算，約 6 人輪流叫，一小時仍回近百則（標準 ≤ 48，Luna 原本的 1/4）。
- 加**頻道層級**的叫她限制：同一頻道 60 秒內被叫 ≥ `CHANNEL_CALL_BURST`（預設 5）次 → 進入「熱鬧模式」2 分鐘：這段期間被叫不每則回，改成收集起來、最多每 `CHANNEL_CALL_GAP`（預設 30）秒回一次，一次回覆把收集到的叫她內容合在一起（沿用現有排隊合併的做法）。熱鬧模式中仍然被叫的會延長模式。
- 單人 tag 限制保留。數字放 config。
- 用 `scripts.eval_chime --only flood`（`--reply-sec 10`）調到 ≤ 48；同時記錄 3 秒、20 秒的結果。如果預設值調不到，報告寫差多少、建議值。
- 單元測試：多人輪流叫觸發熱鬧模式、模式中合併、模式到期恢復。

## 3. 插話判斷對「在講她但不是找她」太容易插話（`yuki/prompts.py` 插話用的 system）
- 錯的 8 題：講她的事（陳述、講開發進度、在別人面前稱讚她）卻判成要接話，participate 0.8～0.9。
- 在判斷標準裡補一條（描述標準，**不放範例句**）：別人在講她、但不是問她、不是邀她回應、也不是在嘴她時，那是別人之間的對話，不算在跟她講話；被問、被挑戰、被邀意見才算。
- 漏插的 others 4 題（有料可接卻給 0.1～0.2）不強求，這條不要改成更積極（Yuki 要比 Luna 安靜）。
- 改完 `scripts.eval_chime --only chime` 跑**兩次**取平均（D-21），代名詞題仍要全對；里程碑／轉貼（`--only milestone`）跑一次確認沒退步。

## 4. 插話速度（中位數 0.696 秒，標準 0.6 秒）
- 先量 prompt 長度、輸出長度哪個佔大宗（`reason` 太長就限制字數；schema 的 `reason` 可設 maxLength）。
- 可以精簡插話用 system 的文字；**最近對話維持 15 則**（不在這次改規格）。
- 第 3 點改完後一起量（同一次 `--only chime` 的結果）。沒達標就在報告寫差多少。

## 5. 回覆開頭夾名字前綴（`yuki/brain.py` `_NAME_PREFIX`）
- 洗版重播 10 則實際回覆裡有 3 則開頭帶名字。先看結果檔（`data/eval_b/results/flood*.json`）確認是哪種形狀。
- 新的回覆關係格式 `[小傑 回覆 阿明「…」]` 可能超過現在正規式的 32 字上限，或模型學了這個格式：讓開頭的 `[…]`（含「回覆」格式）都能被去掉；加單元測試。
- 如果是自然的稱呼（例如開頭叫對方名字再接話），那不是 bug，報告說明即可。

## 6. 真實 80 題退步（平均 73.7%，v5 85%、v6 81.2%）

- 指令：`..\.venv\Scripts\python.exe -m scripts.eval_agentic --cases eval/archive_cases.jsonl --real`（約 10～15 分鐘一次）。
- 只量、不改 B4 的 prompt；結果（有／沒有 B4 的平均）寫進報告。如果拿掉 B4 明顯回升（> 5 點），在報告提出改法建議，不要自己改。
