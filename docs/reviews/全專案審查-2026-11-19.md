## 一句話總評

**6／10**：個別模組（節流、追蹤紀錄、上網防內網、表情後處理）寫得乾淨又有測試，但 `bot.py` 已經變成什麼都管的大物件，幾個隱私保護只擋住了「正門」（`web_search`）卻漏了「側門」（`open_url`、私訊、跨伺服器借資料），prompt 也看得出一輪一輪補洞的痕跡。

分數理由：
- 加分：純邏輯跟 Discord 分開（`throttle.py`、`chime.py` 的 `ChimeLimits`、`trace.py`），可以不連模型就測；隱私有想過（追蹤紀錄寫檔前遮掉退出的人、算不出來就整筆不寫）；錯誤處理大致到位（LLM 錯誤統一成 `LLMError`、工具失敗回文字不丟例外）。
- 扣分：每條隱私規則都有實作，但都只做在一個入口；主伺服器（真正在用的地方）還跑著繞過 B2／B3 的舊行為；兩套檢索並存，約 1200 行舊 RAG 在正式設定下幾乎是死碼但還掛著指令；測試很多是「拿假物件把方法綁上去」驗內部流程，最容易出事的排程／排隊銜接反而沒測。

## 一、嚴重問題（會出錯／會洩漏隱私）

### 1. 「成員名字不准上網搜尋」只擋 `web_search`，`open_url` 完全沒擋
- 位置：`yuki/brain.py:312-321`（agentic）、`yuki/brain.py:249-254`（舊路徑）；`yuki/tools/web.py:152-160`。
- 會怎樣：`names_in(...)` 只在 `name == "web_search"` 時檢查。模型只要改呼叫 `open_url("https://某搜尋引擎/search?q=阿明+某某大學")`，成員名字就直接送到外部網站。`check_public` 只擋內網 IP，不看網址內容。CLAUDE.md 的規則「不准拿成員名字上網搜尋」實際上可以繞過；本機模型在 `web_search` 被擋、拿到 `MEMBER_SEARCH_BLOCKED` 後改用 `open_url` 是合理的下一步，不是假設性的攻擊。
- 建議修法：`call_tool` 對 `open_url` 也檢查 `names_in(unquote(url), names)`（含 query string 解碼後）；被擋回同一句。補一個測試：`open_url` 帶成員名字的網址不會呼叫 `WebTools`。

### 2. 私訊（DM）裡名字過濾等於沒有
- 位置：`yuki/bot.py:400-402`（`members_of(None)` 回 `[]`）、`yuki/brain.py:302,308`（`names` 只剩發言者自己）。
- 會怎樣：任何跟 Yuki 同伺服器的人私訊她「幫我查一下 阿明 念哪間學校」，成員名單是空的，`names_in` 只會擋發問者自己的名字，阿明的名字就送進 SearXNG（再由 SearXNG 送到外部搜尋引擎）。
- 建議修法：私訊時改用「所有 Yuki 所在伺服器（至少主伺服器）的成員名單」當擋名字清單；或私訊直接不給 `web_search`／`open_url`。

### 3. `/不要記我` 只刪「這個伺服器」的資料，但 Yuki 會跨伺服器借資料
- 位置：`yuki/bot.py:886-898`（`gid = guild_key(...)`，只刪這個伺服器）；借資料的地方：`yuki/bot.py:254-259`（測試伺服器查主伺服器封存區）、`yuki/brain.py:265-270` 與 `348-351`（找不到人物檔案就借 `PROFILE_FALLBACK_GUILD` 的）、`yuki/bot.py:411-420`（測試伺服器也認得主伺服器的人）。
- 會怎樣（具體情境）：小美在測試伺服器（或私訊）打 `/不要記我`，畫面回「已刪掉你的檔案、0 則封存訊息」。實際上主伺服器的封存訊息、人物檔案都還在；回到測試伺服器，Yuki 回覆時仍會借主伺服器的人物檔案放進 prompt，`search_chat` 也查得到她在主伺服器講過的話。使用者以為退出了，其實沒有。
  另外追蹤紀錄的退出判斷（`bot.py:167-172`）是「任何伺服器退出就算」，跟其他地方的「只算這個伺服器」不一致，三套語意並存。
- 建議修法：退出改成「以人為單位」：`optout` 查詢不帶 guild，`opt_out` 同時刪所有伺服器的封存與人物檔案；`profile_text`／`pick_profiles` 借檔前先查退出名單；`ArchiveTools` 的 `skip_authors` 參數（目前沒有任何地方傳，見結構問題 6）傳入退出名單。

### 4. 「結束注意模式」的字是用子字串比對、而且看的是頻道裡任何人的話
- 位置：`yuki/bot.py:515-518`；預設字 `yuki/config.py:45`（`掰掰,再見,退下,去睡覺,閉嘴`）。
- 會怎樣：被叫到後 180 秒內，阿凱跟小傑說「我先去吃飯掰掰」或「你閉嘴啦」，Yuki 會在頻道公開回「好的，我先去旁邊休息囉！有事再叫我～」——她根本沒被講到。而且這則因為提早 `return`，**不會進對話紀錄**（`brain.observe` 在後面 `530` 行），之後的回覆看不到這句。「閉嘴」同時也是 `chime._SHUSH` 的字，所以會一次觸發靜音＋退出＋回一句話。
- 建議修法：只在「這則是在跟她講話」（`called`，或回覆她的訊息）時才看結束字；用整句／字首比對而不是子字串；先把訊息放進對話紀錄再 return。

### 5. 人物檔案背景更新可以把聊天回覆卡住最多 10 分鐘
- 位置：`yuki/bot.py:320-323`（背景更新的 client `timeout=max(s.llm_timeout, 600)`，跟聊天共用 `slots`）；`yuki/llm.py:146`（`async with self._slots:` 等待排隊沒有任何上限）。
- 會怎樣：背景更新只在「閒置」時**開始**，但一個請求送出去後就不能中斷。阿明剛好在背景請求跑到一半時叫 Yuki，他的回覆要排在那個最長 600 秒的請求後面；Discord 上只看到「正在輸入」一直轉。同時間插話判斷會因 `llm_is_busy` 全部被跳過（`bot.py:736`）。
- 建議修法：背景更新的單次請求切小、`timeout` 降到跟聊天同級；或在 `LMStudioClient` 做「聊天優先」（背景工作每次送出前先確認沒人在等）；聊天端等排隊加上上限，超過就回「我在忙，等一下」。

### 6. 主伺服器的「注意模式」會一直回、而且繞過熱鬧模式
- 位置：`yuki/bot.py:537-542`（沒開插話的伺服器＝預設主伺服器，注意模式中任何人非雜訊的話都走 `_on_called`）、`bot.py:554`（`count_tag=False` 時 `note_call` 不算，熱鬧模式永遠不會觸發）、`bot.py:631-632`（每次回覆都把 `active_until` 再延長 180 秒）。
- 會怎樣：主伺服器只要有人叫過她一次，之後頻道裡只要有人在 180 秒內繼續講話，她就每一輪都回（忙的時候排隊合併，但一回完就接著回下一批），而且每回一次注意時間又重算，可以一直延續。B3 花力氣做的熱鬧模式在主伺服器完全不生效。程式註解寫明是「維持舊行為」，所以不是意外，但這是正式環境，風險大於測試伺服器。
- 建議修法：主伺服器注意模式至少要走 `note_call`（熱鬧模式）並且不要由「注意模式回覆」再延長注意時間；或直接讓主伺服器也走插話判斷的 attention 路徑。

### 7. 其他會出錯但影響較小的（確認過）
- `/忘記` 成功後在頻道**公開**回「已忘記：<那筆記憶全文>」（`bot.py:872`），等於把要刪的內容再廣播一次。`/記憶` 也是公開回覆（`bot.py:823` 沒有 `ephemeral`），在測試伺服器打關鍵字會用主伺服器的封存區搜，結果貼在測試伺服器頻道（`bot.py:836-841`）。測試伺服器裡是否有主伺服器以外的人：未確認。
- `_respond` 的 `self._replying += 1`（`bot.py:633`）放在 `try` 外面，中間還有 `trace.start`、`emoji_set`、`emoji_pacing.allow` 幾個呼叫。現在這幾個不太會丟例外，但只要有一個丟了，計數就永遠大於 0：所有插話判斷會一直被當成 `llm_busy` 跳過、人物檔案永遠不會再更新（`is_idle` 永遠 False）。屬於「現在沒壞、改一行就壞」的寫法。
- 喚醒詞沒有字邊界（`bot.py:113`，`re.escape(w)` 直接 OR），名字裡含 `yuki` 的字（例如別的角色名）也算叫她。成員名字比對已經改成字邊界（commit `e6dcdb2`），喚醒詞沒跟上。
- `scripts/check_private.py:41-52` 只掃 `HEAD` 這一個版本。如果一次 push 好幾個 commit，中間某個 commit 放了朋友名字、後面又刪掉，`HEAD` 是乾淨的，檢查會過，但名字還是會跟著歷史進公開 repo。
- 設定預設值跟實際使用不一致：`config.py:154` 預設 `RETRIEVAL=embedding`，但 `.env.example:105` 和正式環境是 `agentic`。`.env` 少這一行就會悄悄切回舊 RAG；舊 RAG 的背景記憶寫入（`brain.py:359-376`）完全不看退出名單。`config.py:48` 預設 LM Studio 位址是區網 IP＋1234 埠，跟 CLAUDE.md 寫的 8001 埠不一致。

## 二、結構與維護性問題（依優先順序）

1. **`bot.py` 是 god object（970 行）**。`YukiBot` 同時負責：Discord 事件、斜線指令、語音在場紀錄、語音對話啟停、啟動補抓、人物檔案背景排程、成員名單快取、喚醒判斷、回覆排隊／熱鬧模式排程、插話去抖動、插話判斷整條流程、表情、退出名單的 SQL。每個頻道的狀態散在至少 8 個字典裡：`active_until`、`chime_until`、`_debounce`、`_flush_tasks`、`_chime_tasks`、`throttle` 內部 7 個、`limits` 內部 4 個、`emoji_pacing`。誰負責「佔住頻道」靠註解約定（`bot.py:574`「呼叫端已經 try_start 成功」、`bot.py:717-718`），不是靠結構保證。建議抽出一個「每頻道回覆排程器」（排隊、熱鬧模式、去抖動、busy 擁有權都在裡面），`bot.py` 只做 Discord 轉接。
2. **兩套檢索並存，舊的一套半死不活**。正式設定是 agentic，`Brain.buffer` 在 agentic 下直接 return（`brain.py:362-363`），所以事實記憶、白板不會再更新；但 `/記憶`（無關鍵字時）、`/忘記`、`/白板` 三個指令還在讀這份不再更新的資料（`bot.py:827-833, 859-872, 926-933`）。`memory/`、`rag/`、`embedding.py` 約 1200 行加上 `Brain.reply` 的整個非 agentic 分支（`brain.py:224-262`）只為了舊模式存在。要嘛正式淘汰（指令改成查封存區），要嘛搬到 `legacy/`。
3. **同一段邏輯寫兩次以上**：
   - 借主伺服器人物檔案：`brain.py:265-270` 和 `brain.py:348-351`。
   - `call_tool`（擋名字＋轉呼叫）：`brain.py:249-254` 和 `brain.py:312-321`（這正是第 1 條漏洞兩邊都漏的原因）。
   - 成員別名展開：`bot.py:405-410` 和 `bot.py:415-420`。
   - `ThrottleConfig` 從 Settings 轉換：`bot.py:116-120` 和 `scripts/eval_chime.py:183-189`。
   - 插話判斷的整條關卡（gate → busy → cooldown → decide → kind → try_start / react_gate）：`bot.py:733-806` 在 `scripts/eval_chime.py:230-270` 重寫了一份。評估測的是腳本裡那份，不是 bot 裡那份，兩邊一改就會漂移。
4. **跨物件摸私有成員、事後注入依賴**：`bot.py:323` 拿 `self.brain.llm._slots`、`chime.py:209` 讀 `llm._slots`、`bot.py:749` 用 `self.brain._img_http`、`emoji_catalog.process_reply` 讀 `eset._by_id/_by_key`；`brain.archive_db` 在建構後由 bot 塞進去（`bot.py:133`、`brain.py:128`）。

   - `CHIME_USE_LOGPROBS`（預設關，`config.py:223`）和 `CHIME_EMOJI_LIST`（預設關，`config.py:238`）都是「實測沒比較好」之後留著的開關，連帶 `chime.action_prob/action_dist`、`Decision.prob_source/model_participate/action_dist`、`prompts.CHIME_EMOJI/CHIME_EMOJI_HINT`、`EmojiSet.react_block` 都只在關掉的路徑上。決定紀錄說不用了，就該移除或明確標成實驗。

## 三、測試的問題

整體：338 個測試全過、跑得快、不需要模型，這點很好。問題在「測哪裡」：

1. **最容易出 race 的地方沒有整合測試**。`Throttle` 本身測得很完整（`tests/test_throttle.py`），但 bot 端的 `_on_called → enqueue → _schedule_flush → _flush_later → _run_turns` 銜接沒有任何測試；`test_review_fixes.py` 甚至把 `_on_called` 換成假的（`tests/test_review_fixes.py:39`）。熱鬧模式下「排隊的舊訊息會不會被新的一則插隊、等兩個 gap」（`try_start` 會推遲 `_next_ok`，見 `throttle.py:127-131, 155-157`）這種行為沒有被驗證。
2. **用「把類別方法綁到假物件」的方式測 bot**（`tests/test_chime.py:401-406`、`tests/test_review_fixes.py:21-58`、`tests/test_emoji_use.py:128`）。這種測試緊貼目前的內部屬性名稱，重構就整片壞，但又不保證真實 `YukiBot` 組起來是對的。這也是 `bot.py` 太大的副作用。
3. **測 prompt 字面**：`test_fix8_prompts`（`tests/test_review_fixes.py:200-202`）斷言某句舊字串「不在」prompt 裡、`test_persona_wording_no_sample_sentences`（`tests/test_emoji_use.py:51-55`）斷言一句舊文案不存在、`test_chime_system_has_about_her_but_not_to_her_rule...`（`tests/test_chime.py:563-566`）斷言某個片語存在。這些是「把上一次修改鎖住」，不是驗行為。`test_chime_prompt_has_no_quoted_example_sentences`（`tests/test_chime.py:178-182`）方向對，但只掃三段 prompt，`ARCHIVE_RULES`、`PERSONA`、工具描述都沒掃（而那幾段正好有範例，見第四節）。
4. **測試以審查編號命名**：`test_fix1_...` 到 `test_fix9_...`。測試名稱應該描述行為，不是描述「哪一輪審查修的第幾條」；半年後沒人記得 fix6 是什麼。
5. **重要但沒測的路徑**（都有 grep 確認）：
   - `open_url` 帶成員名字（第一節第 1 條）——`tests/test_chime.py:365` 只測了 `web_search`。
   - 私訊時的名字過濾、私訊時借人物檔案。
   - `/不要記我` 指令本身（只測了 `ArchiveDB.opt_out`，`tests/test_archive.py:19`）；跨伺服器退出完全沒測。
   - 結束字（exit_words）路徑。
   - 背景更新佔住 LLM 時聊天的等待行為。

## 四、prompt 的問題（`yuki/prompts.py`）

1. **違反專案自己的「不要放範例句」規則**：
   - `ARCHIVE_RULES`（`prompts.py:110-112`）給了具體關鍵字組，後面再補一句「不要照抄例子」——這是先放範例、發現被照抄、再加一句禁止的補丁寫法；同一組例子還重複出現在工具描述 `tools/archive.py:22`，那裡沒有「不要照抄」。
   - `prompts.py:119` 直接給了一個完整的回答句型（佔位名字＋月份＋「有說過…」）。
   - `PERSONA` 有引號片語：`prompts.py:16`（兩句嗆人的話）、`prompts.py:51`（兩個時間說法）。
   - 舊路徑 `decompose_user`（`prompts.py:294-296`）、`REWRITE_SYSTEM`（`prompts.py:300-305`）、`WRITER_SYSTEM`（`prompts.py:359-361`）都是完整範例句。
2. **規則互相拉扯**：
   - 身分：`PERSONA` 說「你是台灣人，跟大家一樣在台灣長大」（`prompts.py:29, 36-37`），又說「被問是不是真人不要說自己是真人」（`prompts.py:26`），插話判斷又說她是「成員（AI）」（`prompts.py:198`）。模型要同時維持「在台灣長大」和「不承認是人也不否認是 AI」，容易出現前後矛盾的回答。
   - 成員與上網：`CHIME_SYSTEM` 明確叫模型把「群組成員的事」寫進 `need_background`，格式是「那個人加上事件」（`prompts.py:207`）；這串字接著被 `background_line` 原樣放進回覆 prompt 的「回覆前先查：…」（`prompts.py:145-146`）。等於主動把「成員名字＋事件」做成搜尋主題遞給模型，再靠另外三段文字（`prompts.py:87`、`125`、`146`）和程式端擋名字來阻止它上網搜。前面第 1、2 條的漏洞會讓這個設計直接出事。
   - 表情：`PERSONA` 說「偶爾拿來代替」（`prompts.py:25`），`EMOJI_RULES` 說「九成以上不要用」（`prompts.py:132`），程式端又有 `EmojiPacing` 硬性限制（`emoji_catalog.py` `EmojiPacing`）。三層各寫一個比例；而且 `PERSONA` 這句在沒有表情清單的伺服器也會出現。
   - 記憶：agentic 模式不會放「關於群組成員的記憶」區塊（`prompts.py:185-186`），但 `PERSONA` 還有 5 條講怎麼用那個區塊（`prompts.py:49-53`），在正式環境是指向不存在的東西。
   - 主人：`OWNER_RULES` 承諾主人叫她「安靜一下」會照做（`prompts.py:102`），但回覆模型講了「好」，程式端的靜音只認 `_SHUSH` 正則（`chime.py:34`），插話判斷那邊也看不到這條規則；實際上不會安靜。
3. **補洞痕跡**：`prompts.py:42`「國慶日是 10 月 10 日」、`prompts.py:40` 單一歷史事件的具體描述、`prompts.py:32-33` 一長串「反轉」寫作指導——每一條都像是某次評估答錯後直接塞一行。兩岸段落 14 行，比「講話方式」還長，每次回覆都付這些 token。
4. **評估開關進了正式 prompt**：`prompts.py:163` 讀 `YUKI_EVAL_NO_BACKGROUND_RULES`。

## 五、「像是較弱模型寫的」跡象，以及寫得不錯的地方

### 跡象（具體例子）
- **補丁疊補丁**：`_chime` 為了修「準備資料時 LLM 被佔走」又在中間插一次 `llm_busy` 檢查並提早 return（`bot.py:754-758`），結果同一個函式有兩個寫 `tr.final` 的出口；`_flush_later` 的條件 `ready_in(cid) != 0.0 or not try_start(cid)` 再套一層 `ready_in is not None and not is_busy`（`bot.py:599-602`），拿浮點數跟 `0.0` 比相等來表示「可以回」，很難一眼看懂。
- **為了過評估加特例**：prompt 第四節第 3 點；`CHIME_EMOJI_HINT` 的註解直接寫「只放在 system 裡模型幾乎永遠選 none，放在 user 最後才有用」（`prompts.py:231`），之後整個功能又因評估分數下降被預設關掉，但程式全部留著。
- **測試命名跟著審查走**：`test_fix1`～`test_fix9`，以及斷言「某句舊文案不存在」的測試。
- **重複邏輯導致漏洞成對出現**：`call_tool` 兩份都只擋 `web_search`；借人物檔案兩份都不看退出名單。
- **無效程式碼**：`bot.py:789-790` 的空操作、`should_react(0.0)`、只寫不讀的 `last_seen`、沒人傳的 `skip_authors`。
- **註解跟程式對不上**：`bot.py:97`「只用斜線指令，文字指令前綴用不到」但仍設了 `command_prefix=commands.when_mentioned`（無害但誤導）；`bot.py:661` 註解說「沒有圖鑑也會把 :xxx: 清掉」，但 `process_reply` 在沒圖鑑時會**保留** `<:名稱:ID>` 格式（`emoji_catalog.py` `process_reply` 內 `if eset is None: return m.group(0)`）。

### 寫得不錯的地方（值得保留的做法）
- `throttle.py`：純邏輯、注入時鐘、測試涵蓋洗版／冷卻／熱鬧模式的邊界，結構清楚。
- `trace.py`：追蹤紀錄在 `__aexit__` 寫檔、寫檔失敗不影響回覆、`hide_fn` 寫檔當下才算要遮的字、算不出來就「整筆不寫」（fail-closed），是正確的隱私取捨。
- `tools/web.py`：`open_url` 自己跟每一次轉址、每一跳都檢查是不是內網，防 SSRF 的意識很好（DNS 重新綁定這種進階情況沒處理，未確認是否需要）。
- 全域 `allowed_mentions=NO_PING`（`bot.py:38, 99`），模型吐 `@everyone` 也不會真的 tag。
- `llm.py`：錯誤統一成 `LLMError`、逾時不重試、空回覆的三段補救有清楚註解。
- `archive.py` 退出時連全文索引一起刪；封存只收公開頻道。
- `emoji_catalog.process_reply`：模型亂編的表情名稱一律刪掉，一則最多一個，是「不靠 prompt、靠程式保證」的好例子。
- 測試不需要模型與網路，38 秒跑完，這讓重構有底氣。
